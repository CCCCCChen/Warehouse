# 家用物品管理系统 — 位置管理模块需求文档

> 最后更新：2026-08-03
> 状态：P0 全量完成 / P1-1~5 完成 / P1-6 延后 / P2-5/6 已完成 / P2-4 待实施 / P2-1~3 待排期


## 一、需求概述

在现有家用物品管理系统中，新增 **位置管理** 模块，实现物理空间与数字信息的连接。核心功能包括：空间位置的层级化定义、二维码标签的生成与打印、扫码后的物品查看与录入、位置信息的可视化编辑、移动端录入体验优化。

本文档整合了原始位置管理需求、Bug 修复需求、移动端交互优化需求，并按实施优先级排列。

## 三、P0 详细方案

### P0-1：修复 location_free 提交丢失

**根因**：

```
用户输入 location_free → 拼入 location 串（如 厨房-柜子-上层）
→ 提交时 payload 无 location_free 字段
→ 后端 ItemCreate/ItemUpdate 无此字段 → 无法存储
→ 查询返回后 location_free 无法还原 → 编辑时永远为空
```

整条数据链路断裂。

**修复方案**：

| 层 | 文件 | 改动 |
|----|------|------|
| 数据库 | `models.py` | `ALTER TABLE item ADD COLUMN location_free TEXT` |
| 后端 Schema | `schemas.py` | `ItemBase` 和 `ItemUpdate` 新增 `location_free: Optional[str] = None` |
| 前端提交 | `WarehouseManagePage.vue` | `quickCreate()` / `onSubmit()` payload 增加 `location_free: free \|\| null` |
| 前端回显 | `WarehouseManagePage.vue` | `editItem` → `applyExtracted` 中回填 `it.location_free` 到 `form.location_free`；删除 `location_free: ''` 硬编码 |
| 兼容旧数据 | 展示层 | `location_free` 为 `null` 时降级展示为"无"，不做拆分猜测 |

**⚠️ 与 P0-5 的冲突与协调**：

P0-5 将 `location_free` 改造为 spot 的子选项，并强制拼接 `location = room + '-' + spot + '-' + location_free`。这可能导致 P0-1 中独立存储的 `location_free` 被架空，因为用户只能通过 spot → 子选项的路径填写，无法脱离 spot 单独填写。

**协调策略**：

1. P0-1 的 `location_free` 独立列必须保留，作为**权威数据源**
2. P0-5 实施后，前端仍将 `room`/`spot`/`location_free` 作为展示拼接源，但提交时优先使用 `location_id` 外键关联
3. `location` 拼接字段进入**废弃倒计时**：P0 阶段保留读写以兼容旧接口，P1 阶段标记为只读（仅 GET 返回、不再写入），P2 阶段从 Item 表中移除
4. 位置展示统一从 `Location` 表查询路径，不再依赖 `location` 字符串反解

### P0-2：位置层级 CRUD

**数据模型**：

新建 `Location` 表：

```sql
CREATE TABLE location (
    id          TEXT PRIMARY KEY,
    name        TEXT NOT NULL,
    parent_id   TEXT REFERENCES location(id) ON DELETE CASCADE,
    level       TEXT NOT NULL CHECK(level IN ('zone','wall','unit','sub')),
    zone_id     TEXT NOT NULL,          -- 所属顶层区域ID，冗余存储便于过滤
    path        TEXT NOT NULL DEFAULT '', -- 从根到当前节点的ID路径，如 /loc_1/loc_5/loc_12/
    sort_order  INTEGER DEFAULT 0,
    map_image_url   TEXT,
    coordinates     TEXT,               -- JSON: {"x":200,"y":300,"w":150,"h":120} (千分比)
    household_id    TEXT NOT NULL REFERENCES household(household_id) ON DELETE CASCADE,
    created_at  TEXT DEFAULT (datetime('now')),
    updated_at  TEXT DEFAULT (datetime('now'))
);
```

`Item` 表新增外键列：

```sql
ALTER TABLE item ADD COLUMN location_id TEXT REFERENCES location(id) ON DELETE SET NULL;
```

保留旧字段 `room`/`spot`/`location` 作为只读展示，后续版本逐步废弃。

**迁移策略**：

启动时 `ensure_location_table()` 执行：
1. `CREATE TABLE IF NOT EXISTS location`
2. `ALTER TABLE item ADD COLUMN location_id`（仅当列不存在时）
3. 将 `HouseholdConfig` 中 `rooms_json` / `area_map_json` 的旧数据转为 `Location` 记录
4. 尝试匹配 `item.room` / `item.location` 到 `Location.name`，更新 `item.location_id`

**API 设计**：

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/locations` | 获取位置树（按 household_id 过滤，支持 `?zone_id=` 筛选子树） |
| `POST` | `/api/locations` | 创建位置（自动计算 zone_id、level，检测循环引用） |
| `PUT` | `/api/locations/{id}` | 更新位置（name/coordinates/map_image_url/sort_order） |
| `DELETE` | `/api/locations/{id}` | 删除位置（级联子位置，关联物品 location_id 置 NULL） |
| `POST` | `/api/locations/{id}/move` | 移动位置（更改 parent_id，重新计算 level 和 zone_id） |
| `POST` | `/api/locations/batch-delete` | 批量删除空位置 |

**循环引用检测**：利用 `path` 字段实现 O(1) 检测。移动位置时，只需检查目标节点的 `path` 是否**不以**当前节点 path 为前缀，同时 `LIKE '{current_path}%'` 确认自身不在目标子树中。

**path 字段价值**：除循环检测外，`path` 可直接用于面包屑导航渲染（`SELECT * FROM location WHERE id IN (拆分 path)`），无需逐层递归查询，极大加速深层位置的路径展示。

### P0-5：录入页 location_id 预填 + 位置补充交互改造

**扫码预填**：

`WarehouseManagePage.vue` 接收 URL query 参数 `?location_id=xxx`：

1. `mounted` 时调用 `GET /api/locations/{id}` 获取位置详情
2. 解析位置层级：zone → wall → unit → sub
3. 自动填充 `room`（zone 名称）和 `spot`（wall + unit 名称）
4. 若有 `sub` 层级 → 填充到 `location_free`
5. 位置字段置灰（`:disabled="!!$route.query.location_id"`），不可修改

**location_free 交互改造**：

将 `location_free` 从独立输入框改为 spot 选择框的子选项：

```
选择收纳位（spot）: [柜子 ▼]

┌─ 如果选择可细分收纳位 ──────────┐
│  细分位置: [第2层    ]（选填）   │  ← location_free
└─────────────────────────────────┘
```

提交时强制拼接：`location = room + '-' + spot + (location_free ? '-' + location_free : '')`，同时 `location_free` 独立提交（P0-1 已确保存储不丢失）。


## 四、P1 详细方案

### P1-1：编辑跳转滚动定位

**问题确认**：

```
用户点击列表中某物品的 [编辑] 按钮 →
  entryOpen = true（表单在列表上方静默展开）→
  editItem()（数据填充到表单）→
  用户屏幕仍停留在列表区域，完全不知道表单已就绪
```

移动端（卡片式全屏列表，`max-width: 900px`）尤为严重。用户点击卡片编辑后需手动向上滚动过 stats + filters 才能看到表单。

**修复方案**：

`ItemsPage.vue` 的 `editInEntry` 方法，展开 entry-wrap 后滚动定位：

```javascript
editInEntry(it) {
  this.entryOpen = true;
  this.$nextTick(() => {
    if (this.$refs.entry && typeof this.$refs.entry.editItem === 'function') {
      this.$refs.entry.editItem(it);
    }
    // 滚动定位到表单顶部
    const entryEl = this.$el.querySelector('.entry-wrap');
    if (entryEl) {
      entryEl.scrollIntoView({ behavior: 'smooth', block: 'start' });
    }
  });
}
```

同时给 `entry-wrap` 添加短脉冲高亮动画（蓝色边框闪烁 0.6s），强化视觉感知。

### P1-5：连续录入模式（仅保留位置字段）

**保留范围**：仅位置相关字段（room / spot / wall_side / wall_slot / location_free）。

**不保留**：type_l1 / type_l2 等分类字段。依据：录入场景通常是"同一位置但不同类别"的物品，保留分类反而不便。但考虑到"同一位置+同一类别"的衣柜整理等场景，增加可配置能力。

**保留策略可配置**：连续录入面板底部增加 **"同时保留分类"** 开关（勾选后 type_l1/l2 也不清空），开关状态持久化到 `localStorage`。默认关，满足主流"同位置不同类"场景；需要"同位置同类"时一键开启。

```javascript
resetFormForContinuous() {
    const keep = {
        room: this.form.room,
        spot: this.form.spot,
        wall_side: this.form.wall_side,
        wall_slot: this.form.wall_slot,
        location_free: this.form.location_free,
    };
    Object.assign(this.form, this.getEmptyForm(), keep);
    this.$nextTick(() => this.$refs.nameInput?.focus());
}
```

触发条件：URL 带 `location_id` 参数时自动启用，或用户手动开启"连续录入"开关。

## 五、P2 详细方案

### P2-1：AI 关联物品自动填充

**目标**：替代手动从下拉列表挑选关联物品，由 AI 自动分析推荐。

```
用户保存物品 →
  提取物品特征（name + type_l1 + type_l2 + room + spot）
  → 调用 LLM（复用 ark_ocr.py 火山方舟接口）
  → 在已有物品库中匹配最相关的 3-5 个物品
  → 自动写入 related_item_ids
  → 用户可在物品详情中查看/手动调整
```

触发时机：创建或更新物品时异步执行（不阻塞保存）。

兜底策略：AI 不可用时降级为基于规则（同类别 + 同位置）的简单匹配。

---

### P2-2：AI 识别后台队列 + 推送通知

**问题**：当前 OCR 识别是同步阻塞的（拍照 → 上传 → 等待 3-8 秒 → 返回），移动端体验差。

**目标流程**：

```
拍照 → 提交到后台队列 → 立即返回"识别中"
       ↓
  用户可以继续浏览/操作其他内容
       ↓
  后台完成识别 → 生成"待完善物品"草稿
       ↓
  通知用户：
    1. 仪表盘顶部通知横幅："识别完成，N 件物品待完善"
    2. 物品列表顶部"待完善"筛选标签，高亮数量
       ↓
  用户点击通知 → 跳转录入页 → 表单已预填 AI 识别结果 → 补充确认后保存
```

**数据模型**：

新建 `ItemDraft` 表：

```sql
CREATE TABLE item_draft (
    id TEXT PRIMARY KEY,
    household_id TEXT NOT NULL,
    extracted_json TEXT,       -- AI 识别出的字段 JSON
    image_path TEXT,           -- 原始照片路径
    status TEXT DEFAULT 'pending',  -- pending / confirmed / discarded
    created_at TEXT DEFAULT (datetime('now'))
);
```

**后端 API**：

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/ocr/item_extract_async` | 接收图片，入队，返回 draft_id |
| `GET` | `/api/drafts` | 获取当前家庭待完善草稿列表 |
| `GET` | `/api/drafts/{id}` | 获取草稿详情（含 AI 提取字段） |
| `POST` | `/api/drafts/{id}/confirm` | 确认为正式物品 |
| `DELETE` | `/api/drafts/{id}` | 丢弃草稿 |

**队列实现**：不使用内存队列，改为**数据库轮询**，利用已有 `item_draft` 表作为天然持久化队列：

后台 daemon 线程每 2s 扫描 `SELECT * FROM item_draft WHERE status='pending' LIMIT 1`，逐条调用 LLM 识别后更新状态为 `completed` / `failed`。服务重启后自动从 `pending` 继续处理，不丢任何任务。SQLite 需确保 worker 线程使用独立连接，避免并发写冲突。

> 基础同步 OCR 流程先保持不变，P2 再做异步队列和通知。

## 八、风险与注意事项

| 风险点 | 应对 |
|--------|------|
| P0-1 与 P0-5 逻辑冲突 | location_free 独立列作为权威数据源；location 拼接字段进入废弃倒计时（P0 读写 → P1 只读 → P2 移除）；展示从 Location.path 拼接 |
| 循环引用检测性能 | Location 表增加 path 字段（如 `/loc_1/loc_5/`），循环检测改为 LIKE 前缀匹配 O(1)，同时加速面包屑导航 |
| 内存队列数据丢失 | 废弃 queue.Queue，改用 item_draft 表轮询作为持久化队列，服务重启后自动从 pending 接续处理 |
| 连续录入场景覆盖不全 | 面板底部增加"同时保留分类"开关持久化到 localStorage，兼顾两种录入习惯 |
| 旧数据兼容 | Item 表保留 room/spot/location 旧字段只读；迁移脚本尽力匹配，匹配不上则 location_id=NULL |
| SQLite 并发 | Location 表操作频率不高，SQLite 足够；worker 线程对 item_draft 使用独立连接 |
| 移动端适配 | 扫码面板和地图标注页使用 viewport + touch-action，所有按钮 ≥44pt 触控区 |
| 二维码安全性 | 面板页面不要求登录，但操作跳转后触发路由守卫进行 Token 鉴权 |
| AI 识别超时 | 设置合理超时（15s），超时后标记为失败，用户可手动重试或手动填写 |
| P2-5/6 实施中的 transition 闭包 | Python 脚本批量添加 `</transition>` 时，最后 section 因后续为注释/表单闭合而非新 section，正则未命中；手动补充闭合标签 |
| P2-6 household_id 获取失败 | `GET /api/me` 失败时静默降级为 `'default'` key，不阻塞正常使用 |
